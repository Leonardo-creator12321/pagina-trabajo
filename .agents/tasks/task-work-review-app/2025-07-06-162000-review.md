# Greenfield work-review platform for a game dev team

A complete Next.js 16 application with Supabase backend that implements role-gated work submission and review. A CEO views developer cards and approves/rejects submissions; developers upload files (PDF, image, video) or text notes and track their status. The architecture follows the standard Supabase SSR pattern: middleware refreshes the session on every request, server components fetch data directly, and client components call API routes for mutations. Storage uploads go through the browser client directly to Supabase Storage.

**Watch for:** The storage bucket is created as private but `getPublicUrl` is called on every upload, which returns a URL that won't resolve without either making the bucket public or using signed URLs (confirmed). The CEO's detail page fetches all submissions for an arbitrary developer ID without verifying that ID belongs to a developer role, allowing the CEO to probe any UUID (likely). There are zero automated tests (confirmed).

## High-level view

Authentication uses Supabase's `signInWithPassword` on the client, session refresh via middleware, and role lookup from the `profiles` table. Role-based access control lives entirely in individual page components and API routes (not in middleware), creating a surface where new routes could forget the check.

File uploads go directly from the browser to Supabase Storage via the `work-evidence` bucket. The upload path is `{userId}/{timestamp}_{filename}`, which provides per-user isolation. However, the bucket is private and the code uses `getPublicUrl` (which only works for public buckets), so files will be inaccessible in production until this is resolved with signed URLs or a bucket visibility change.

The profile lifecycle has a gap: there's no trigger or signup flow that creates a `profiles` row when a user registers through Supabase Auth. The app only works with pre-seeded accounts. New users hit an infinite redirect loop between `/dashboard` (no profile → redirect to `/login`) and middleware (authenticated → redirect away from `/login`).

When `fileType === 'note'`, the `SubmissionForm` overwrites the `description` field with note content, silently discarding any description the developer entered. The UI shows both inputs simultaneously, which is misleading.

## Private bucket vs. public URL mismatch

The migration creates the storage bucket as private:

```sql
INSERT INTO storage.buckets (id, name, public)
VALUES ('work-evidence', 'work-evidence', false)
```

But `FileUploader.tsx` retrieves the public URL after upload:

```typescript
const { data: urlData } = supabase.storage
  .from('work-evidence')
  .getPublicUrl(filePath);
```

For a private bucket, `getPublicUrl` returns a well-formed URL that 403s on access. The CEO's submission list renders file links and the `FilePreview` component embeds images/videos using these URLs. In production, all file previews and downloads will be broken. The fix is either changing the bucket to `public = true` (acceptable if all authenticated users should see files) or generating signed URLs server-side with an expiry when the CEO or developer views a submission.

## Developer detail page accepts arbitrary IDs

The CEO detail page at `/dashboard/developer/[id]` fetches the developer profile by the URL parameter:

```typescript
const { data: developer } = await supabase
  .from('profiles')
  .select('*')
  .eq('id', id)
  .single();
```

It checks that the result exists but never verifies `developer.role === 'developer'`. If someone navigates to `/dashboard/developer/{ceo-uuid}`, the page would render the CEO's own profile as if they were a developer. Supabase RLS allows the CEO to read all profiles and all submissions, so there's no backend guard either. Add `.eq('role', 'developer')` to the profile query.

## Note submission overwrites description

In `SubmissionForm.tsx`, the submission body is built with a description field from the textarea. But for notes, the code overwrites it:

```typescript
if (fileType === 'note') {
  body.description = textContent.trim();
}
```

If a developer enters both a description and note content, the description is silently lost. The data model doesn't have a dedicated `content` column for notes, so the workaround of using `description` is understandable, but the UI still shows both fields simultaneously. Either hide the Description field when "note" is selected, or add a `content` column to the schema.

## Profile lifecycle gap

The seed file inserts profiles with hardcoded UUIDs, but there's no mechanism for a newly registered user to get a profile row. The redirect loop manifests as:

1. User logs in → middleware lets them through to `/dashboard`
2. `/dashboard` queries `profiles` for the user → returns null
3. Page redirects to `/login`
4. Middleware sees authenticated user at `/login` → redirects to `/dashboard`
5. Loop

Either a Supabase database trigger on `auth.users` insert should create the profile row, or a signup page should handle profile creation.
